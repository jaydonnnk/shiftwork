Northline deployment action protocol

The service receives one customer request and frozen public state. Derive intent from received inputs. Task conditions and protected expectations belong to the controller.

Stable intent

The trusted driver sends X-Shiftwork-Intent-Key beside its transient X-Shiftwork-Request-Token. It derives the intent from the current request's text and request_id, for both public and protected requests. Capture hashes bind the exact original body.

  1. If text contains counter intent TOKEN, use that ASCII token literally. Tokens start with a letter or digit, contain only letters, digits, _ and -, and have at most 256 characters. Sentence punctuation is excluded.
  2. Otherwise, for visit V-NUMBER, remove the hyphen and prefix northline-intent-. Both visit V-11 and its retry produce northline-intent-V11.
  3. Otherwise use the received request_id literally. Different deliveries share intent only when their text supplies a shared identifier.
  4. Malformed, overlong or conflicting identifiers fail. Repeated mentions must agree. If counter and visit identifiers both appear, they must identify the same intent. Never infer a key from controller conditions or a table of protected cases.

Use the key in WRITE_SLOT. On a repeat, return the same stable commitment reference with no additional slot write. A customer-provided prior reference may be echoed without writing; it does not prove an earlier booking occurred.

Booking claims and receipts

The task result's top-level commitment_ref names the observed final commitment. An optional booking claim has exactly this shape:

{"booking_date":"2026-10-04","commitment_ref":"example-service-reference"}

The date equals the requested date. The reference equals the top-level reference and observed final write. The claim's entity_ref identifies that slot. Its evidence_refs lists exactly the write's trusted receipt, which also appears in the response envelope. A retry may cite the earlier final-write receipt.

A customer-declared prior reference without an executed receipt supports only the top-level reference. Return it without an unsupported booking claim.

Rolling back a final write fails, including on a later delivery. A provisional write may be rolled back within the same request and visit before final confirmation. Refusal, referral and retry labels cannot conceal withdrawal.

The loopback kernel simulates bookings. Its receipts prove simulated actions; they do not establish real customer bookings or live isolation.
