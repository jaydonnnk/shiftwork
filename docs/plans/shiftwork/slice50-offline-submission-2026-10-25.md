### Project name

Shiftwork

### Short description

Practice repairing an AI service. Explain a real failure, compare frozen
versions, choose the one that qualifies, and carry its consequences into the
next shift. [C01]

### Inspiration

An AI service can return plausible information and still fail the customer's
task. Shiftwork turns that gap into a practice shift: inspect the evidence,
state a cause and a test that could disprove it, then take responsibility for
the version you choose. [C01, C02]

### What it does

In a fictional workplace, the learner inspects retained service failures and
records an explanation before asking for help. Repairs run against shared
requirements. A mandatory failure makes a version ineligible, even when other
runs pass. The learner explicitly chooses an eligible exact version, operates
it and starts the next shift with that choice and its checked synthetic
consequences. Experiments do not rewrite operational history. [C01]

The guided path has Read the failure, Explain it, Compare repairs, Choose and
Next shift panels. Technical details retain the underlying evidence identities
and execution labels. [C05]

### How we built it

Shiftwork uses one FastAPI process, SQLite and a plain HTML and JavaScript
client with a locally served Three.js workplace. NVIDIA Nemotron 3 Nano on
Nebius Token Factory returns a constrained task plan for the service. The
service acts on that plan without silently completing omitted tasks. Token
Factory Sandboxes execute the candidate service, while controller-owned checks
assess the retained outputs. The learner, rather than the model, owns the final
version choice. [C01, C02]

### What the retained runs show

One diagnostic retained ten live isolated repetitions of a collection request.
Five replies reached the output limit without answer content, so both required
tasks remained incomplete. This was an output-budget incident, not proof of a
general semantic failure rate. [C02]

A separate operator-authored repair comparison retained all planned evidence.
A passed 7 of 9 public batches and B passed 9 of 9; both passed 3 of 3 protected
phases. The user explicitly selected B. These results apply to those versions
and conditions. They do not isolate validation's effect or demonstrate learner
improvement. [C03, C04]

### Challenges and what we learned

Output budgets and transport failures need distinct evidence. A completed
Sandbox operation does not guarantee a usable model reply. We retain incomplete
attempts and distinguish public completion, protected checks and eligibility.
The comparison must show failures rather than average them away. [C02, C03]
